# Sales Portal Codex prompt for Chamber sponsorships

Implement Chamber Event Highlight administration in the existing KRTR Sales Portal, the Next.js app in `apps/sales` at `sales.krtrlocal.tv`. Inspect its existing server authentication, owner/admin permissions, deployment configuration and district setup before coding. The app has its own Supabase project. Confirm which Sales roles should administer sponsorships using existing project conventions, and enforce that authorization on each server-side read and write.

The public-site/CMS app at the repository root already owns the shared records. Use its server-to-server API in `app/api/nrcs/chambers/route.ts` through the canonical CMS host. Store the base URL and dedicated bearer credential as server-only Sales environment variables. Coordinate setting the matching secret as `CMS_SALES_CHAMBER_API_SECRET` on the public/CMS Vercel project. Use a dedicated random secret and keep it out of browser code, logs, and source control. The NRCS publication credential is separate. Confirm the target host in each environment by inspecting the existing NRCS-to-CMS publishing configuration.

- `GET /api/nrcs/chambers` returns `{accounts, coverage, districts}`. Accounts contain `id`, `name`, `city`, `active`, `contact_name`, `contact_email`, `contact_phone`, and `notes`. Coverage rows contain `chamber_id`, `district_key`, and `active`. District options contain `district_key` and `display_name`. This response contains private account information. Keep it inside authorized Sales admin views and disable caching.
- `POST /api/nrcs/chambers` accepts `{account, coverage}`. Send the full account record and an object mapping CMS district keys to booleans, for example `{"dlpc":true,"vs":false}`. Reuse the existing UUID on updates and generate one UUID per new account intent, retaining it across retries. Names may repeat. Require name, city, account active status and valid district keys. Allow blank contact fields and notes. Omitted previously assigned districts are disabled and retained. The receipt is `{id, affected_districts}`. Use timeouts, refuse redirects on authenticated fetches, and show failures in the admin UI.
- The CMS database stores `chamber_accounts` and `chamber_district_coverage`. The coverage primary key is `(chamber_id, district_key)` with foreign keys to `chamber_accounts.id` and `districts.district_key`. Use CMS district keys from the API, including `dlpc` for Dysart–La Porte City/Union coverage, and confirm any mapping to Sales district records. The CMS server role invokes `save_chamber_account(jsonb,jsonb)`. The API expires affected district caches through `lib/publicCache.ts`, including the global fallback for `dlpc`. Route all Sales changes through this same API. Keep account and coverage records authoritative in CMS.
- NRCS separately stores `chamber_id` and `chamber_highlight_type` on its existing single-district event rows. The public event projection stores the same pair and resolves the current label in `chamber_event_label(events)`. Keep event editing, event publication, and public rendering in their current apps. The package uses event-level gold borders and labels.

Implement the authorized list, create, edit, account status, contact, and per-district coverage workflows using existing Sales UI conventions. Include tests for unauthenticated and unauthorized access, known district keys, independent district activation, duplicate display names, stable UUID retries, and errors from the shared API. In a test environment, create and update an account from Sales, read the same record in NRCS, publish a test event with each highlight type, and verify the public calendar after a rename and after activation/deactivation in each covered district. Check that the cache refreshes on Sales writes and contact fields do not appear in public responses. Keep the temporary NRCS administration page available during integration and verification.

Request explicit approval after the Sales implementation is deployed and verified. After approval, set `NRCS_CHAMBER_ADMIN_ENABLED=false` on both the NRCS and public/CMS deployments, then redeploy them. This retires the NRCS navigation, page, server action, and NRCS credential access to admin GET/POST. It preserves the NRCS catalog GET used by the event form and the dedicated Sales credential. Verify the NRCS admin route and write access are disabled, then verify Sales can still administer the same records and refresh public caches. Confirm an NRCS editor can still assign, remove and publish an event highlight. Preserve existing records and IDs throughout the handoff. Document any Sales environment variables, role decisions, and outstanding verification.
